# Security Policy

## Supported Versions

Security fixes are provided for the latest published release of `cc-safety-net`.

If you are using an older version, please upgrade to the latest version before reporting an issue unless the vulnerability also affects the latest release.

## Security Model and Invariants

CC Safety Net is a best-effort, static pre-execution policy gate for supported coding-agent tool calls. It is not an operating-system sandbox, a privilege boundary, or protection for commands that bypass an installed integration. An agent and the command text it supplies are untrusted; the user's policy, pinned rulebook state, configured roots, and adapter-established execution context are trusted inputs.

The current implementation preserves these product invariants:

- Command-execution capability is granted only to exact tool names, built-in or user-declared: each adapter's integration-specific shell tools, plus tools the user lists in `command_tools` in `rule.json`. A declaration applies only to a tool the adapter routed as unknown and only when its input carries a non-empty string `command`; it is analyzed like a built-in shell tool at the user's own safety level. Its working-directory argument (`workdir`, `cwd`, `working_directory`, or the declared name) may name any existing directory, as with the DeepSeek Harness, Amp, and Gemini CLI adapters, rather than being confined to the session workspace. An omitted argument uses the session workspace; a blank, non-string, conflicting, or nonexistent-directory value is denied. A declaration with `"cwd": false`, for a tool whose working directory is on another machine, reads none of these arguments, including the OpenCode `workdir` and Cursor `working_directory` arguments those adapters otherwise resolve for every tool, and analyzes its command against the session workspace, so a relative path such as `rm -rf build` is judged as if it were inside that workspace, not in the remote working directory. Other unknown tools retain conservative policy-file and sensitive-path inspection without treating arbitrary text as a shell command. This is covered by `tests/gate/intake.test.ts`, `tests/gate/pipeline.test.ts`, `tests/hosts/hook/common.test.ts`, `tests/hosts/opencode/plugin.test.ts`, `tests/hosts/cursor/hook.test.ts`, and `tests/hosts/pi/tool-call.test.ts`.
- The canonical user `policy.json` receives best-effort static protection against direct write, edit, and patch targets; exact shell operands and write redirections; supported environment, relative, and existing symlink aliases; recursive `rm` of its directory or an ancestor; and `mv` when the file, its directory, or an ancestor is a source. Rulebooks, lockfiles, caches, sibling files, and policy-directory inspection are intentionally outside this guard. Core and integration coverage lives in `tests/gate/guards/policy-protection.test.ts`, `tests/hosts/opencode/plugin.test.ts`, and `tests/hosts/pi/tool-call.test.ts`.
- The nearest ancestor Git control-plane entry, resolved linked-worktree or submodule Git directories, common Git directory when available, and their `hooks` subtrees receive best-effort static protection against the supported delete, move, redirection, write-tool, and patch routes. Other repositories below the execution directory and Git-internal paths outside this set are not protected by this guard.
- Sensitive-path protection applies across supported command, path, search, and patch shapes, including unknown-tool fallback inspection. See `tests/gate/secret/secret-protection.test.ts` and the hook, OpenCode, and Pi integration tests above.
- Destructive-command decisions are semantic and context-sensitive: nested execution, working directory, shell mode, safety options, disabled built-ins, and custom rules affect the result. `tests/gate/contract.test.ts` records a small representative contract; the remaining `tests/gate/analyzer/` suites provide exhaustive edge coverage.
- User policy is authoritative. Project rulebooks may add restrictions but cannot weaken user-scoped rules. Remote rulebooks are resolved through pinned lock and digest state. These behaviors are covered by `tests/core/policy/merge.test.ts` and `tests/rules-manager/sync.test.ts`.
- Runtime evaluation loads a deeply immutable policy snapshot from local policy, lockfiles, and verified caches. It performs no repair writes, network requests, or in-memory caching; synchronization remains an explicit CLI operation. See `tests/core/policy/snapshot.test.ts` and the fail-closed-to-sync integration coverage.
- Invalid configuration resolves to one of two runtime states, and never denies ordinary work. `ready` enforces every validated source. `degraded` means a candidate source was rejected and something safe is enforced in its place: an unverifiable rule source is dropped so it contributes no rules, a duplicate rulebook name keeps the first claim, and an unreadable policy file falls back to the salvaged policy or to built-in protective defaults. The rejected candidate is never treated as active, and the fallback is reported in audit metadata, `doctor`, the GUI and status surface, `rule list`, and an appended warning on the next denial — on decisions made after the configuration snapshot is loaded; the always-on policy-file and Git metadata protections carry no config state, and deny before config load except for an unknown tool whose input carries a `command`, where the snapshot loads first only to decide whether the tool is a declared command tool. Dropping a source removes the denials that source contributed. That is a real reduction in enforcement relative to the configured policy, and it is the accepted cost of not locking the agent out; it is not presented as a security-neutral outcome. What dropping cannot do is weaken a built-in rule or permit something the built-ins block: rulebooks contribute only blocking rules and no wrapper metadata, and ignoring an unreadable `rule.json` restores the built-ins its `overrides` would have disabled. The resulting posture is that of a machine with no rulebook configured, which is why the state is reported on every surface rather than absorbed silently. One exception is scoped and documented: `transparent_wrappers` lives in `rule.json`, so an unreadable `rule.json` narrows which wrapped commands built-in analysis unwraps for that scope. `rule.json` carries no lock or digest by design, so no verified copy exists to fall back to, and an agent can already delete that key from a readable file in the ready state without a diagnostic, which places the gap inside the tamper boundary below rather than outside it. A dropped rulebook cache, missing lock entry, or digest mismatch leaves wrapper metadata intact. No command or path is allowlisted in return, because nothing is denied for being unconfigurable. See `docs/config-recovery.md`, `tests/core/policy/snapshot.test.ts`, `tests/gate/pipeline.test.ts`, `tests/gate/intake.test.ts`, `tests/hosts/opencode/plugin.test.ts`, and `tests/hosts/pi/tool-call.test.ts`.
- Tamper resistance covers the canonical user `policy.json` only. Custom rule configuration — `rule.json`, rulebooks, lockfiles, and caches — is best-effort against agent modification: in the ready state an agent can already remove a rulebook entry from `rule.json`, and removal is not drift, so nothing gates it. This is why denying every tool call on unverifiable rule configuration was removed rather than kept: an actor that wants those rules gone already has an unguarded path, so the denial protected nothing and only stranded the user. Adding protection for `rule.json` is a deferred product decision and is not part of the current model.
- Audit records and denial messages are redacted best-effort for recognized credential forms before serialization. Redaction is defense in depth for values the tool call itself supplied: an unrecognized credential form or an unredacted field is an ordinary bug, not a vulnerability. Audit paths, serialization, decision metadata, and redaction behavior are covered by `tests/audit/writer.test.ts` and the integration audit tests.
- False-positive reports prepared in the GUI replace the entry's own working directory and the user's home directory with `<project>` and `~` before the report is displayed. Substitution requires a path boundary, so sibling directories and unrelated paths sharing a prefix are left intact rather than rewritten. Nothing else is scrubbed: absolute paths outside those two prefixes, hostnames, and branch or remote names are carried through. The report is shown in an editable preview, prefills a GitHub issue form only on explicit user action, and issues no network request itself. Coverage lives in `tests/gui/report.test.ts`.
- On Windows, untrusted cwd-selection and recursive-delete operands that select Win32 UNC or device namespaces are rejected before filesystem access. Trusted roots, including namespaced roots established by an adapter, and relative paths beneath them remain supported.
- Untrusted recursive tool input is bounded to 64 object levels, 10,000 visited values, 10,000 own keys, 1 MiB per string, and 4 MiB of aggregate string data. Hook stdin is capped at 8 MiB of raw bytes. Exceeding either boundary fails closed.
- `GIT_CONFIG_COUNT` is capped at 1,024 entries. Malformed counts and incomplete key/value pairs fail closed before linked-worktree relaxation.
- Rule synchronization accepts at most 64 configured sources and resolves at most four sources concurrently while preserving configured order. Repository discovery and subsequent resolution share one nonconfigurable operation budget of 131 GitHub requests and 64 MiB of successfully read response bytes. Each request rejects redirects, has a mandatory 15-second timeout covering both fetch and body consumption, and retains per-response bounds of 512 KiB for metadata, 256 KiB for commit metadata, 16 MiB for repository trees, and 4 MiB for rulebook content. `Content-Length` and streamed per-response bytes are enforced before rulebook validation or digest use. A resolver failure stops new source work, aborts standards-compliant in-flight fetches, and drains work that already started before returning.
- Rulebook acceptance limits are fixed and nonconfigurable: at most 1,024 allowed commands, 1,024 rules, 2,048 fixtures, 1,024 block arguments per rule, 16,384 block arguments total, 1,048,576 UTF-16 code units per supported string, 4,194,304 supported string code units total, and 131,072 code units per fixture command. Validation retains at most 64 detailed errors. Fixtures are shape-validated and never executed. Inputs over any limit fail closed with a fixed diagnostic before policy cache or lock publication.

The current public command analyzer returns `null` when it allows a command and an `AnalyzeResult` when it blocks one. It does **not** expose the parser's internal `complete`, `partial`, or `limited` states. Unsupported or malformed shell syntax is safety-level dependent: standard mode may allow malformed safe-looking text, while strict mode blocks unparseable input; destructive-looking malformed text can still be blocked by conservative heuristics. Parser resource exhaustion is different: input beyond 131,072 UTF-16 code units, more than 16,384 words, or nesting beyond 64 levels is denied rather than analyzed incompletely.

Standard, Strict, and Paranoid are safety presets that supply defaults. Standard mode is best-effort protection for recognizable destructive commands and intentionally allows dynamic executables, guarded command structure assembled through substitution, unverifiable recursive-delete targets, and metadata-only checks of built-in sensitive paths (`ls`, `stat`, `test -e`/`-f`, `[ -e`/`-f ]`, `git check-ignore`, `find` without actions, `wc` counts with only `-l`/`-w`/`-c`/`-m` or their long forms, and `grep`/`rg` limited to file names, counts, or exit status by `-l`, `-L` (grep only), `-c`, `-q`, or their long forms, without a `-f` pattern file, an `rg --pre` preprocessor, or a `--json` or `--format` output option), alone or as one segment of a compound command; a `wc`, `grep`, or `rg` whose output can reach a pipe (a pipe later in the command, including one after an enclosing subshell, brace group, conditional, loop, or called function, or any pipe beside a heredoc read as shell), whose output is captured by command substitution or by an interpreter's execution call, or whose command holds a coprocess (`coproc` or `|&`), is still checked, and a `grep` names-only flag counts only before the first operand, because a non-permuting `grep` reads a later `-l` as a file. For built-in sensitive-path rules standard mode also does not treat as a read: a secret file name that names an existing directory, a word containing whitespace that neither starts like a path nor exists on disk (command or prose text, such as `for c in 'cat ~/.aws/credentials'`), an output redirection that creates a secret-named file where none exists, a `mkdir` or `touch` operand, including one holding an unresolved expansion (every operand of a `touch` given `-r`/`--reference` and every redirection target is still checked), a `tailscale cert` `--cert-file` or `--key-file` value, also after `sudo`/`env` or as `timeout <n> tailscale cert`, the input file of `openssl x509 -in`, which prints only certificate data whatever the file holds (inputs of other `openssl` subcommands such as `rsa`, `pkey`, or `pkcs12`, and every other `x509` file option, stay checked; because `tailscale` prints the names it writes and `x509` reports a failed input name, both stay checked where their output can reach a pipe, a coprocess, or a capture, unless every command in the command line is `cd`, `grep`, `head`, `tail`, `openssl`, or `tailscale`, also after `timeout <n>`, and it holds no command or process substitution), or a `for` list word whose loop variable reaches no other checked word, such as `for t in .env.local; do grep -c -- "$t" notes.md; done`. A list word stays checked when the variable, a `${!` indirection, or a word equal to its name (a nameref) appears in another checked word (a reader operand, redirection, assignment value, substitution body, inline interpreter code, or nested loop list), when the loop or a segment naming the variable comes before a pipe, or when the command holds process substitution or a coprocess; a name the loop writes to a file that a later command reads back, or copies with `printf -v`, is not followed, like the same commands without the loop. A display command such as `echo` after `do`, `then`, `elif`, `else`, `if`, `while`, `until`, or `!` is judged as it is at the start of a command. A command holding process substitution gets neither the `mkdir`/`touch` nor the `wc`/`grep`/`rg` relaxation. Home-directory and coding-CLI credential rules are never relaxed for directories, file creation, or certificate inputs. The one exception is the identity file `ssh`, `scp`, or `sftp` reads with `-i` before its first operand, which is not a read for any built-in rule, home-directory rules included, because the key is used only to authenticate and never printed; `-F`, `-o` values such as `IdentityFile=` or `ProxyCommand=`, the remote command, and `scp`/`sftp` source operands stay checked, and an `scp` or `sftp` given `-S`, which passes the identity file to that program, gets no exception. Standard mode also allows `eval` and `source` of a single fully literal local generator command, such as `eval "$(ssh-agent -s)"`, `eval $(opam env)`, or `source <(kubectl completion bash)`, after the substitution body itself passes analysis. Only the generator command's shape is verified — the shell it emits at runtime is executed unverified, so this extends trust to the output of every literal local command, including forms like `eval "$(cat somefile)"`; any dynamic word, compound or redirected body, remote-fetching head such as `curl` or `wget`, or shell or wrapper head stays blocked, and strict and paranoid modes deny every dynamic shell source unconditionally. Sensitive content access and user-configured deny paths, including their descendants, remain blocked. Strict and paranoid modes fail closed on those forms and metadata-only sensitive-path discovery, and are required when commands may come from prompt injection or other adversarial context.

In every safety level, disk-device destruction is a protected category: `dd` with `of=` a device, the `mkfs`, `mke2fs`, and `newfs` families on a `/dev/` target, `diskutil` erase and partition verbs, `wipefs -a`/`-o`, `sgdisk` writes, `parted` label and partition edits, and output redirects onto a literal disk device path are blocked; further disk tools are added on field evidence.

In every safety level, built-in extension rules such as `.pem` or `.asc` do not apply to URL query text: a word holding a query parameter (`?key=` or `&key=`) that names no existing file, or the value after a query's `=`. A file with such a name that exists stays protected. A curl data or form value (`-d`, `--data`, `--data-ascii`, `--data-binary`, `--data-urlencode`, `-F`, `--form`) is checked only as the `@file` or `<file` upload it names.

For every non-shell interpreter's inline, heredoc, or stdin code, standard mode treats string literals as inert diagnostic or test data when the code as a whole contains no recognizable filesystem, command-execution, or eval marker. When the code holds such a marker, Python and JavaScript literals are judged by their position: a list, set, or tuple element, a dict key or value, an object property value, a subscript key, an operand of `in`, `not in`, `==`, or `!=`, or a whole argument of `print(` or `console.log(` is data, unless the code binds `print` or `console` (an assignment, `def`, `function`, `class`, `import`, `as`, `const`, `let`, or `var`) or uses either name other than as a call. The whole value of a statement-level assignment (`name =`, or `const`, `let`, or `var name =`) is data when every other use of that name is in a data position, such as `note = 'credentials'; print(note)`. Every other position, such as another call argument, any other assigned value, or a return value, keeps the literal as a candidate. A Python `#` comment is not code, so quotes and brackets inside it change no position. Positions are not read, so every literal stays a candidate, when the code holds a JavaScript comment containing a bracket, a `/*` comment, unpacking or spreading of a bracketed collection (`*(`, `*[`, `...[`), or a method call named like a keyword, such as `.of(`. When the code names a command-execution function or module (an identifier part starting with `exec` or `spawn`, or `popen`, `system`, or `subprocess`), list and tuple elements and `print(` or `console.log(` arguments stay candidates too. A literal that only names the file a write creates is relaxed like an output redirection, only where no such file exists: a direct `Path(...)` or `pathlib.Path(...)` argument immediately written with `.write_text(` or `.write_bytes(`, the first argument of a bare `open(` whose mode is a literal holding `w`, `x`, or `a` without `r` or `+`, or the first argument of `writeFile`, `writeFileSync`, `appendFile`, `appendFileSync`, or `Bun.write`; the same name anywhere else in the code that is not data keeps it a candidate. Data and write literals are exempt only from built-in file-name rules such as `.env`, `*.pem`, or `credentials`; home-directory and coding-CLI credential paths remain candidates in any position, and so does a literal an execution call receives. Standard mode does not follow a data literal to a later read, so a file-name secret held in a collection and opened afterwards, such as `for f in {'.env'}: open(f)`, is allowed. In other interpreters' code one marker anywhere keeps every literal as a candidate. Standard mode walks a literal as shell text only when an execution call receives it: every literal when the call's first argument is or holds a name, otherwise the literals inside the call's parentheses or after a parenthesis-less `system`/`exec`. A first argument that is a list or tuple of only plain literals and names, whose first element (the program) is a literal, counts as holding no name when no element is a shell or interpreter name or a `-c`, `-e`, `-r`, `-E`, `--eval`, or `--exec` flag, such as `subprocess.run(['ffprobe', '-v', 'error', f])`; a program that runs an argument as a command line itself, such as `['watch', cmd]` or `['ssh', host, cmd]`, is not followed, like `watch` and `ssh` in shell commands. Destructive text uses the name boundary without that list exception: a dangerous command written as a string literal blocks only when an execution call can receive it, or when the code holds backticks, `%x`, or `qx`. At every level, a native recursive delete whose first argument is a literal root path or a home expression such as `os.path.expanduser('~')`, `$ENV{HOME}`, `os.homedir()`, or `Dir.home` blocks as `interpreter.dangerous-command`: Python `shutil.rmtree`, Perl `rmtree` or `remove_tree`, Node `rm`, `rmSync`, `rmdir`, or `rmdirSync` with `recursive: true`, and Ruby `FileUtils.rm_rf`, `rm_r`, `remove_dir`, `remove_entry`, or `remove_entry_secure`; a computed or joined target is not resolved (RR-4). Strict and paranoid modes keep every literal unconditionally and also inspect inside literal text. Configured deny paths and their descendants are never relaxed, and opaque or custom access wrappers remain outside standard mode's non-adversarial guarantee.

Heredoc bodies are data unless something executes them. In standard mode an unquoted heredoc whose body expands only variables, with no `$(…)` or backtick substitution, is treated like a quoted one, and a script written from it is still analyzed if a later command runs it. `uv run python -` and an interpreter reading its program from `-` followed by script arguments are recognized as stdin programs. Strict and paranoid modes keep failing closed on unquoted heredocs.

When standard mode cannot verify a command — unparseable text holding a destructive pattern, or a shell execution source it cannot resolve that is neither a shell reading stdin nor a command whose text names a destructive pattern — the Claude Code hook asks the user through Claude Code's permission prompt instead of denying, but only in the `default`, `acceptEdits`, `plan`, and `auto` permission modes, where the prompt reaches a person; in `auto` mode Claude Code's classifier may still deny the call but cannot approve it without the prompt. Every other mode, every other host, and strict and paranoid modes keep the deny. Hosts are left on deny when their `ask` fails open (Codex, Cursor, Kimi Code) or may be answered automatically.

In standard mode, xargs input spliced into a `sh -c` body is a data word when it never starts a command and the body stays harmless with `/` in its place; input carrying shell syntax of its own is crafted input, outside standard mode's guarantee. Strict and paranoid modes treat every such body as dynamic.

Trusted user policy may configure `destructive_command_protection.allow_paths`: absolute or `~/`-prefixed directories whose contents are treated like trusted temporary roots for recursive-delete analysis (`rm`, `Remove-Item`, `find -delete`), in every safety level. Allow paths never relax secret protection or deny paths, never apply to dynamic or unverifiable targets, and never cover root, home, or protected Git metadata targets. Entries equal to or containing the home directory are rejected at validation and again after symlink canonicalization at analysis time; targets are canonicalized best-effort before matching, so a symlink escaping an allowed directory is not covered. Allow paths are a deliberate, user-scoped relaxation: anything a command deletes beneath them is outside CC Safety Net's protection.

Catastrophic protections are always enforced: recursive deletion of root, recursive deletion of the user's home directory, destructive mutation of the protected Git metadata set, and destructive mutation of the canonical user policy file. They do not depend on safety level, the destructive-command master switch, per-rule overrides, or allow paths.

Trusted user policy may explicitly set a registered built-in destructive-command rule to `"on"` or `"off"`. For non-catastrophic rules, the destructive-command master switch wins first, followed by the rule override and then the resolved preset capability. An `"off"` override for a catastrophic rule remains valid policy syntax but is ignored. These per-rule controls do not change the documented threat-model boundary, do not apply to custom rules or secret patterns, and do not independently control fail-closed parser or sensitive-path outcomes that have no registered destructive-command rule ID. Consequently, Strict with all five Strict-tier destructive-command rules off is still Strict for those non-rule outcomes.

PowerShell support is partial. Its parser preserves native quoting, path separators, connectors, pipelines, and dynamic-word provenance for a conservative subset: `Remove-Item` and its supported aliases, the file cmdlets `Get-Content`, `Set-Content`, `Add-Content`, `Copy-Item`, and `Move-Item` with the aliases `gc`, `cat`, `type`, `cp`, and `mv`, plus existing cross-shell command rules; it is not a general PowerShell parser. Sensitive-path checks resolve a `$HOME`, `$env:USERPROFILE`, `$env:HOME`, or `~` prefix joined to a literal suffix by either path separator, for positional operands and space-separated parameter values; an expression assembled any other way, including concatenation, a subexpression, `Join-Path`, and a colon-joined parameter value, is not evaluated and not covered. In `auto` mode, a `ForEach-Object` or `Where-Object` command also selects the PowerShell parser, so its script block is read as PowerShell. Explicit `powershell` mode and quote-aware `auto` detection are covered by `tests/core/shell/parse.test.ts` and the PowerShell path-expression cases in `tests/gate/secret/secret-protection.test.ts`, while `posix` mode intentionally does not apply PowerShell removal rules outside a nested `powershell` or `pwsh` script.

A `cmd /c` or `cmd /k` body (including `cmd.exe` and Git Bash's `//c`) is read by a bounded check, not a cmd parser, in both shell modes. The body is split on `&` and `|`; `rmdir`, `rd`, `del`, and `erase` with `/s`, anywhere in a piece (including after `@` or an `if` condition), are judged by the recursive-delete target rules against the outer working directory, with a final `*.*` segment read as `*`, and every other piece is analyzed as a command of the outer shell. A body that holds such a delete is blocked in every permission mode by `cmd.recursive-delete-escaped-quote` when it contains a backslash-escaped quote (under PowerShell, one inside a word of the original command), any `"` in posix mode (Git Bash re-escapes it as `\"` for cmd), or a `\\?\` or `\\.\` namespace path, because cmd does not treat `\"` as an escape and the target can split down to the drive root. Otherwise its targets are judged first and a matching target rule denies; only when nothing else blocks it is it refused as an unverifiable shell source, which asks the user where the host can prompt, when it contains `^`, `%`, or `!`, a `"` together with `&` or `|` (the body is split without regard to quotes), or a `cd`, `chdir`, `pushd`, or `popd` word anywhere, glued forms such as `cd..` included. A body whose text names `rmdir`, `rd`, `del`, or `erase` and an `/s` switch that the reader cannot parse as a delete, such as `rd/s/q`, a quoted command name, `call`, `for`, or a parenthesized group, is refused the same way when nothing else blocks it. These checks read the body text without parsing it, so they can also refuse an inert mention such as `echo rmdir /s /q C:\`. Batch file contents and delayed expansion are not read.

A `powershell` or `pwsh` invocation (any case, with or without `.exe`) is read in both shell modes only in one shape, not by a PowerShell command-line parser: zero or more of `-NoProfile` (`-nop`), `-NonInteractive` (`-noni`), `-NoLogo`, and `-ExecutionPolicy` (`-ep`) with one value, then `-Command` or `-c`, then script words that are all literal, with no expansion by the outer shell. That script is analyzed as PowerShell against the outer working directory, and its verdict is the verdict. Any other invocation, including another parameter, a `/` or Unicode-dash prefix, `-WorkingDirectory`, `-File`, a positional script, or an expanded word, is blocked in every permission mode by `powershell.nested-recursive-delete-unread` when its text names a delete command (`Remove-Item`, `ri`, `rm`, `rmdir`, `rd`, `del`, or `erase`) and a recursive switch (`-r…`, `--r…`, or `/s`) as words, and is otherwise allowed. Outside a read script, any word naming `-EncodedCommand` (an abbreviation such as `-e` or `-enc`, the `-ec` alias, or a `/` or Unicode-dash prefix) is refused as an unverifiable shell source, which asks the user where the host can prompt. `-File` script contents and scripts read from stdin are not read.

Codex support is bounded by the host's unified exec design, which is the default shell path. Codex sends a `PreToolUse` payload for `exec_command` but none for `write_stdin`. Text written into an already-running interactive session therefore reaches the shell without inspection and without an audit entry; only the command that opened the session is evaluated. No adapter change can close this gap, because the host supplies no event for that call.

The Codex `exec_command` payload carries only `{command}`, and its `cwd` is the turn directory. Codex runs the command in the call's `workdir` argument, which the payload omits, so CC Safety Net analyzes that command against the turn directory. Relative paths and outside-directory rules can then be judged against the wrong directory, in either direction. Closing this gap requires the host to include `workdir` in the payload.

OpenClaw `exec` calls whose `host` is `auto` or absent are analyzed with local Gateway filesystem semantics, because Gateway is the only proven path mapping and an absent host is the default shape on every install without a sandbox. On a sandbox-configured install the host resolves `auto` to the sandbox, so such a command executes in the container while its analysis and audit record describe Gateway paths. An explicit `host: "sandbox"` request for that same execution is failed closed.

OpenClaw runs `exec` in the session's working directory, which can differ from the agent workspace: a managed-worktree session runs in its checkout, by default under `<state>/worktrees`, and a session created with a `cwd` runs there. The `before_tool_call` hook context exposes no working directory, so the adapter anchors every `exec` call at the agent workspace. In such a session a command without `workdir` is analyzed against the workspace but runs in the session directory, a relative `workdir` is resolved against the workspace instead of the session directory, and an absolute `workdir` outside the workspace, such as the session's own worktree, is failed closed. Closing this gap requires the host to expose the execution directory.

OpenClaw's `openclaw agent exec` command never loads the plugin hook registry, so no `before_tool_call` hook runs and its tool calls are neither analyzed nor audited, even when the plugin is installed and loaded. The same tool call through `openclaw agent --local` is blocked.

Kimi Code sends the server process directory as the payload `cwd` for `kimi web` and ACP sessions, not the session's own directory, and the payload carries no other working directory. In those sessions every `Bash` call is analyzed against the directory the server was launched from: relative paths and outside-directory rules are judged against the wrong directory, in either direction, and a `cwd` argument naming the session directory is denied as outside when that directory is not inside the server's launch directory. Terminal `kimi` sessions are unaffected. Closing this gap requires the host to send the session directory.

On Windows, OpenCode v1 converts a POSIX-rooted `workdir` such as `/tmp` with `cygpath -w` when it runs a POSIX shell, while the adapter resolves it against the current drive, such as `C:\tmp`. Such a call can be analyzed against a different directory than the one it runs in.

Grok Build hooks are fail-open by design, and the host exposes no `failClosed` knob to change that. Only an explicit deny decision on stdout blocks a tool call; a hook that crashes, times out, or emits malformed output lets the call proceed. The adapter therefore emits an explicit deny for its own fail-closed outcomes, such as truncated tool input or an unusable working directory, but a failure that prevents the adapter from producing output at all is not a block on this host.

Factory Droid hooks fail open. Only exit code 2 or an explicit deny decision on stdout blocks a tool call; any other non-zero exit, a crash, a timeout, or a missing `npx` is logged as a non-blocking error and the call proceeds. The adapter emits nothing for an allowed call, so Droid's own permission prompt still applies. An enterprise `allowManagedHooksOnly` setting ignores user and project hooks, so the hook that `install --droid` writes to `~/.factory/hooks.json` does not run under it. The hook was verified against `Execute` and the file tools; `Task` subagents, `Loop`, and automation tools have not been verified to reach it.

Devin CLI hooks fail open. Only exit code 2 or a `block` decision on stdout blocks a tool call; a timeout, a missing `npx`, or a hook process that dies before printing a decision lets the call proceed. Errors the adapter catches itself still produce a `block` decision. The adapter emits nothing for an allowed call, so Devin's own permission prompt still applies. Only the user-level config that `install --devin` writes (`$XDG_CONFIG_HOME/devin/config.json`, by default `~/.config/devin/config.json`, or `%APPDATA%\devin\config.json` on Windows) is supported: its hooks run in the session directory, while hooks in a project `.devin/hooks.v1.json` run with the repository root as their working directory, and the payload carries no `cwd` to correct that. Each `write_to_process` call is analyzed on its own, so a command split across several writes to an interactive shell is outside the analysis. In `bytes_input`, only `<CR>` and `<LF>` end a line. A call that carries text in either field together with any other key (`<ESC>`, `<BS>`, an arrow key, or a `<C-…>` key) is denied, because the line the receiving program runs cannot be known; those keys alone, such as `<UP><CR>` or `<C-c>`, are not analyzed. An undocumented key token, or text in both `text_input` and `bytes_input` of one call, is also denied. Devin Cloud sessions are not covered. Devin also loads Claude Code hook files by default, so a CC Safety Net hook installed for Claude Code may run there as well, which only duplicates denials.

DeepSeek Harness loads CC Safety Net as an optional profile plugin that registers a monotonic tool guard, which runs after every `tools/pre-execute` listener, including approvals and Auto review, and can only deny. The host treats a failed import or `apply()` of an optional plugin as a warning and keeps running, so a profile whose bundle fails to load runs unprotected; `doctor` reads the profile manifests, not the running host. Desktop keeps its own `desktop` profile, and its crash-recovery action disables third-party bundles until they are re-enabled. `install --deepseek-harness` adds the plugin to the `web` and `desktop` profiles only; the `acp`, `headless`, `sdk`, and `sdk-minimal` profiles, and any profile created later, run without CC Safety Net unless the plugin is added to them with `dsh plugin --profile <name> add cc-safety-net`. In PTC mode, off by default, `run_code` executes model-written TypeScript with direct Node.js APIs; only its tool sub-calls reach the guard. The opt-in terminal tools write `terminal_send` text into a persistent shell without analysis, and a persistent `bash` or `pwsh` tool keeps directory changes across calls while each call is analyzed against the session workspace.

Policy-file protection is deliberately a minimal exact-path guard, not command emulation or an operating-system security boundary. It tracks only simple assignment-only shell variables and explicit `cd` changes needed to resolve direct paths. It does not infer computed interpreter paths, inspect interpreter bodies, expand shell globs or braces, infer archive members, simulate `find` actions, infer remote filenames, or infer a transfer's final filename from its destination directory. Malformed shell input is blocked by this guard only when the canonical policy path remains directly extractable; parser resource exhaustion still fails closed. The hard-stop message, `This path contains the protected policy config and you must not modify or delete it.`, is guidance to the agent, not a claim of complete filesystem enforcement. Use a trusted write broker, operating-system permissions, a sandbox, or equivalent runtime enforcement when complete protection is required.

The structural command IR is produced by the bounded internal POSIX and PowerShell parsers. No third-party shell parser is embedded in the published JavaScript artifacts.

## Reporting a Vulnerability

Please do not report security vulnerabilities in public GitHub issues.

Use GitHub private vulnerability reporting for this repository when available. If that is unavailable, email the maintainer at jliew@420024lab.com.

Include as much detail as you can safely share:

- The affected `cc-safety-net` version
- Your operating system and runtime version
- The affected integration, such as Claude Code, OpenCode, Gemini CLI, GitHub Copilot CLI, Grok Build, Factory Droid, Devin CLI, or Codex
- Steps to reproduce the issue
- The input that makes CC Safety Net leak a secret, write outside its intended directory, or distribute tampered code
- Any relevant output from `cc-safety-net explain` or `cc-safety-net doctor`
- Whether the issue can cause data loss, command execution, secret exposure, or another concrete security impact

Please redact tokens, credentials, private repository names, and sensitive file paths before sending logs or command output.

## The Boundary: Bug or Vulnerability?

CC Safety Net's job is to stop agents from running destructive commands within the selected safety level's documented guarantees. A report that the tool failed to do that job is a **bug**, and it belongs in a public GitHub issue. The strict and paranoid threat model assumes an attacker (prompt injection, adversarial context) can emit any destructive command, so publishing "this command shape is not caught" does not hand the attacker a capability they did not already have — it just gets the gap fixed faster and lets users ship a custom rule as an immediate workaround.

A report that the tool did something harmful it was never supposed to do — disclose a secret its caller did not already hold, write a file outside its own directory, or ship a tampered package — is a **vulnerability**. The non-obvious construction is the secret, so it belongs in private disclosure.

The dividing line is: **did the tool fail to stop a destructive command, or did the tool itself become the harmful vector?**

## What Counts as a Security Issue

Report these privately:

- Disclosure of a secret the tool call did not supply, such as file contents or environment values the tool read, through block messages, audit logs, diagnostics, or debug output
- A false-positive report prefill that carries a path the report preview claims to have replaced
- A path traversal or filesystem issue in audit logging or configuration handling, where crafted input writes outside the intended directory
- A supply-chain or packaging issue affecting the published npm package or plugin distribution, including rulebook integrity

## What Should Be Reported Publicly Instead

Use normal GitHub issues for:

- Any bypass or fail-open that lets a destructive command execute — a coverage gap (a command the rules do not block yet), a parser, tokenizer, or wrapper-analysis edge case, or an analysis error that lets a command through instead of blocking it. Report the command _shape_, not a ready-to-paste weaponized prompt-injection payload.
- Redaction gaps: a credential form the redactor does not recognize, or a field it does not cover, when the value came from the tool call itself and appears only in the denial message returned to that caller or in the local audit log
- False positives where a safe command is blocked
- Missing convenience rules or new feature requests
- Documentation bugs
- Installation problems without a security impact
- Questions about custom rules or configuration

Findings from Anthropic's OSS Scanner, including bypasses, are confidential under that service's terms. The maintainer fixes them privately and opens a public issue only after the fix is released.
